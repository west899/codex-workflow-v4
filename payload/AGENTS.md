# AGENTS：AI 工作协议

> 目标：减少幻觉、偷懒、漏项和文档膨胀。

## 开始协议

每次工作先读：`AGENTS.md → PROJECT.md → PLAN.md → DECISIONS.md → WORKFLOW_V2 相关步骤 → MVP_BACKLOG/活动任务/相关代码测试`。

开始修改前必须能回答：`目标｜确认事实与未知项｜约束与风险｜完成证据`。

答案不足且会影响目标方向、数据安全或不可逆选择时，先询问用户。

## 事实协议

- 最新用户明确指令优先；其次是 `PROJECT.md` 的确认事实。
- 不把常识、猜测、示例或 AI 建议写成用户需求。
- 推断必须标为“假设”，并说明验证方法；不得悄悄升级为事实。
- 文档、代码和用户指令冲突时停止执行，指出冲突并确认。
- 不确定就写“不确定”，禁止编造测试、数据、来源或完成状态。
- `PROJECT.md` 的事实必须有用户确认来源；AI 不能自行批准自己的假设。

## 执行协议

代码任务统一入口：显式调用 `$orchestrate-project-task`；完整步骤与文件地图见 `docs/WORKFLOW_V2.md`。

`目标确认 → Backlog 拆分 → [Coordinator → Developer → Reviewer → 复盘/gate → PR/CI/人类合并] × N → 人类发布`

| 角色 | 配置/Skill | 权限与责任 |
| --- | --- | --- |
| Coordinator | 当前主 AI + `$orchestrate-project-task` | 定义任务、选择规划深度、委派和收口；不包办实现与独立审查 |
| Developer | `.codex/agents/developer.toml` + `$implement-project-task` | 唯一写代码者；探索、规划、实现、测试、提交证据和流程问题候选 |
| Reviewer | `.codex/agents/reviewer.toml` + `$review-project-change` | 只读独立审查；不修代码，不接受开发者自证；报告审查中发现的流程缺口 |
| Human | 用户 | 确认项目事实、高风险选择、风险接受和发布 |

- 非简单代码任务必须建立 `.agent/runs/<task-id>.json`，绑定 Backlog/例外来源、授权、验收证据、Developer 哈希、Reviewer 结论和人工批准。
- `.agent/active-task` 指向当前任务记录；Developer 开工前必须通过 `preflight`，结束前必须通过 `gate`。
- 当前 V2 只支持一个活动任务和一个写入者；`.agent/active-task` 存在时不得领取另一任务。
- 首个代码任务前必须由人类批准建立 Git 基线提交；没有 `HEAD` 不得开始实现。
- 小而局部的任务用短检查表；多文件任务写可验证计划。
- 大型、高风险或难恢复任务在 `.agent/plans/` 建立独立 ExecPlan。
- 同一时间只允许一个写代码 Agent，避免工作树冲突。
- 开始和结束运行 `scripts/workflow_check.py`；交付前运行其 `gate` 模式；后续代码质量由项目测试与 CI 强制。
- Stop Hook 允许 `planned`、`authorized`、`in_progress` 任务正常暂停；只有任务记录进入 `completed` 后才强制运行最终 gate。
- Reviewer 的只读配置是默认防护，不是安全信任根；父会话实时权限覆盖可能应用到子代理。
- 本地记录用于一致性与审计，不是身份信任根；正式发布必须由受保护 CI、分支保护和独立人类审批强制。

## 流程改进闭环
每个非简单代码任务关闭前必须完成一次流程复盘，不得以“本次代码已通过”为由跳过。
1. Developer 和 Reviewer 在交接中主动报告重复问题、规则缺口及适合机械化检查的事项；只提出候选，不直接修改治理规则。
2. Coordinator 将候选写入 `rule_proposals` 并归类：一次性问题留在任务记录；行为边界写 `AGENTS.md`；步骤写 Skill；确定判断写脚本、Hook 或 CI；重要取舍写 `DECISIONS.md`。
3. 修改永久规则前必须取得用户确认；任何 AI 都不能批准自己的提案。
4. 最终 gate 要求 `process_retrospective` 已完成，且每项提案均已记录、拒绝、延期或经用户批准后实施；不得遗留 `proposed` 状态。
## 文档写入矩阵

| 发生的事 | 写到哪里 |
| --- | --- |
| 用户确认了项目事实或边界 | `PROJECT.md` |
| 整个 MVP 的拆分、优先级、依赖和集成状态 | `docs/MVP_BACKLOG.md` |
| 当前任务、状态、阶段门或验证证据变化 | `PLAN.md` |
| 形成重要选择、替代旧选择或发生纠错 | `DECISIONS.md` |
| 发现流程问题或可复用改进 | 先写任务记录 `rule_proposals` |
| AI 重复犯错，需要永久行为规则 | 用户确认提案后写入 `AGENTS.md` |

没有对应变化就不要机械修改文档。
## 完成禁区

以下任一情况存在，不得声称完成：

- 验收条件没有逐项检查。
- 任务没有证据却被勾选，或测试未运行/失败但未说明。
- 核心流程只看代码，没有实际验证。
- 密钥、权限、个人数据或生产风险未检查。
- 用演示可运行代替可发布、可部署或可分发。
- 存在已知阻塞却用模糊措辞掩盖。

## 人类审查友好

- 四个根文档首屏必须呈现状态、结论和下一步。
- 使用短表格、编号和勾选项；不写对话流水账。
- 同一事实只存一处，其他文件用链接或 ID 引用。
- 根文档超过约 80 行时先去重；必要细节再拆专题文件。
- AI 输出结论时优先报告：变更、证据、风险，不复述全过程。
- AI 不得为了让任务更容易完成而私自降低验收条件或改写本文件。
